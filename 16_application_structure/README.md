なぜアプリケーション構造が必要なのか

小さなサンプルコードでは問題にならなくても、

エンドポイントが増える

共通処理（ログ・認証・設定）が増える

チームでコードを触るようになる

といった状況になると、
1ファイルにすべてを書く設計は限界を迎えます。

アプリケーション構造を考える目的は次の3つです。

見通しをよくする

責務を分ける

変更の影響範囲を小さくする

よくある状態：main.py が太る

学習初期によくある状態は、次のような構成です。

app/
└── main.py


この中に、

すべてのエンドポイント

バリデーション

ログ設定

エラーハンドリング

が書かれていくと、
**「どこを見れば何が分かるのか」**が分かりづらくなります。

FastAPIにおける基本的な分割の考え方

FastAPI では、アプリケーションを次のように分割していくことが一般的です。

app/
├── main.py
├── routers/
│   └── items.py
├── schemas/
│   └── item.py
├── services/
│   └── item_service.py


この分割は「正解」ではありません。
しかし、考え方としてとても重要です。

構造を分けると何が嬉しいのか
1. main.py の役割が明確になる

main.py は、

FastAPI アプリを作る

ルーターを登録する

という 起点の役割 に集中します。

2. 「何をしているコードか」が一目で分かる

routers：HTTPとの境界

schemas：データの形

services：処理の中身

ディレクトリを見るだけで、
コードの責務が想像できるようになります。

3. 変更に強くなる

エンドポイントが増えても routers に追加するだけ

処理を変えても services を触ればよい

変更の影響が局所化されます。
